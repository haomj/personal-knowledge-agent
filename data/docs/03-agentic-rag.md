# Agentic RAG：检索、评分与查询改写

传统 RAG 的流程是：检索一次，然后把结果交给模型生成答案。Agentic RAG 在此基础上增加了“判断”和“重试”，让 Agent 能发现检索结果不足并改进查询。

## 基本流程

```text
用户问题
  -> 检索知识库
  -> 判断相关性
     -> 足够：生成带来源的回答
     -> 不足：改写查询
              -> 再次检索（最多一次）
              -> 生成回答
```

## 文档加载与切分

第一版只支持 Markdown 和 TXT。加载时保留 `source` 元数据，回答时才能显示来源。切分要兼顾语义完整和检索粒度，常用参数是 `chunk_size` 与 `chunk_overlap`。中文文档可以使用段落、标题和句号作为分隔符。

## Embedding 与向量库

Embedding 把文本映射成向量，向量库按相似度检索。Chroma 是本地轻量向量库，适合单机学习环境。集合创建后维度固定，换 Embedding 模型时需要重建集合。

## Retrieval Grading

评分节点判断“检索到的文档是否足以回答问题”。可以用 LLM 做语义判断，返回 `sufficient` 和 `reason`。如果没有任何文档，可以直接判定不足，不必调用模型。

评分不是越严格越好：过于严格会频繁触发改写，增加延迟和费用；过于宽松会把无关内容交给生成模型。

## Query Rewriting

当检索不足时，改写节点把用户问题改写成更适合检索的查询。改写可以：

- 补全代词和上下文；
- 展开缩写；
- 提取关键词；
- 去掉口语化表达。

必须限制重试次数，否则可能陷入无限循环。常见的上限是 1 次改写、2 次检索。

## 带来源的回答

生成节点的提示词要明确要求：

- 只根据检索到的内容回答；
- 使用 `[来源: 文件路径]` 标注；
- 信息不足时明确说明，不要编造；
- 不要把无关文档强行引用。

来源信息应该同时保存在 State 中，方便 CLI 或 Web UI 单独展示。
